# PTL Trader — Portfolio Import File Format

This is the reference for the JSON file accepted by **File › Import Portfolio…**.

Today such a file is produced by the **Export to JSON** button in the Pair Trading
Lab (PTL) Portfolio Manager. **Pair Trading Lab is shutting down**, and once it is
gone there will be no tool generating these files. This document exists so the
format stays usable afterwards — so a file can be written by hand, generated by a
script, or produced by some future exporter, without reading the website's source.

The same shape is written by PTL Trader's own **File › Export Portfolio…**, and is
what PTL Trader stores in its local database. An exported file always re-imports
cleanly.

A representative example produced by the PTL website is included in this
repository as `portfolio.json`.

For how this document relates to the internals — the database column it is stored
in, and the `updateFromJson()` methods that read it — see
[TECHNICAL.md §6.1](TECHNICAL.md). This file is the authoritative description of
the *file*; TECHNICAL.md describes the code around it.

---

## 1. Top-level structure

The file is UTF-8 JSON containing **either** an array of portfolio objects **or** a
single bare portfolio object:

```json
[ { "name": "My Portfolio", "...": "...", "strategies": [ ... ] } ]
```

Both forms are accepted. The website's export and PTL Trader's own export both
emit a one-element array. Multiple portfolios in one array are imported together.

Each portfolio object carries its settings plus a `strategies` array, each element
of which is one pair strategy. The `strategies` array must be present and must be
an array; it may be empty, which imports an empty portfolio.

---

## 2. What the importer changes

Import **always creates a new portfolio**. It can never modify or overwrite an
existing one, and can never disturb a strategy that currently holds an open
position. To that end, four things in the file are deliberately not honoured:

| In the file | What import does |
|---|---|
| `uid` (portfolio and every strategy) | **Regenerated.** A fresh UUID is assigned to the portfolio and to each strategy, so importing the same file twice gives two fully independent portfolios rather than a collision. |
| `account_code` | **Cleared to `""`.** A broker account binding from another machine is meaningless locally; binding to a live account must be a deliberate act in the UI. The field must still be *present* (`null` is fine). |
| `features` | **Dropped.** This was the PTL website's per-portfolio/per-strategy feature-gate list. PTL Trader has no feature gating and ignores it. |
| `last_opened_datetime`, `last_opened_equity`, `last_model_state` | **Stripped.** This is runtime state describing an open position in an account the import is not bound to. An import can never seed position state. |

Any other field the importer does not recognise is left in the stored document but
never read. The PTL website's export includes several such columns from its own
database — `invert`, `transform`, `inv_transform_a`, `inv_transform_b`,
`bid_ask_spread_1`, `bid_ask_spread_2`. They are harmless, and omitting them
changes nothing. They are not documented further here because PTL Trader has no
code that reads them.

---

## 3. Portfolio object

All six fields below are **required** — a missing one rejects the file. The four
marked numeric must hold a number (or a JSON boolean; see §6).

| Field | Type | Meaning |
|---|---|---|
| `name` | string | Display name. Not otherwise constrained. |
| `max_pairs_open` | number | Slot count: how many pairs may hold a position at once. Also the divisor in per-pair margin allocation. |
| `account_alloc` | number | Percent of account equity this portfolio may allocate (`100` = all of it). |
| `account_code` | string or `null` | Broker account binding. Must be present; the value is cleared on import. |
| `master_status` | number | `0` inactive, `1` maintain (manage open positions, open no new ones), `2` active. |
| `pdt_rules` | number | Pattern-day-trader protection: `0` disabled, `1` enabled (25 k rule). |
| `strategies` | array | The pair strategies. Required, may be empty. |

Optional/ignored: `uid` (regenerated), `features` (dropped).

---

## 4. Strategy object

Every field in this section is **required** unless the row says otherwise. A
missing required field rejects the whole file, naming the offending strategy as
`ticker1/ticker2`.

### 4.1 The pair

| Field | Type | Meaning |
|---|---|---|
| `ticker1` | string | First leg, `EXCHANGE:TICKER` (see §5). |
| `ticker2` | string | Second leg, same format. |
| `trade_as_1` | number | `0` trade leg 1 as stock/ETF (`STK`), `1` as CFD. |
| `trade_as_2` | number | Same for leg 2. |

### 4.2 Model selection and thresholds

| Field | Type | Meaning |
|---|---|---|
| `model` | string | One of exactly `Ratio`, `Residual`, `Kalman-grid-v2`, `Kalman-auto`. Any other value rejects the file. |
| `entry_threshold` | number | Z-score at which a position is opened. |
| `exit_threshold` | number | Z-score at which it is closed. |
| `downtick_threshold` | number | Z-score band used by the downtick entry mode. |
| `max_score` | number | Upper z-score bound; a signal beyond this is treated as too extreme to enter. |
| `neutrality` | number | `0` dollar-neutral, `1` beta-neutral. |

### 4.3 Per-model parameters

All of these must be present regardless of which `model` is selected — the
parameters belonging to other models are simply unused.

| Field | Type | Used by | Meaning |
|---|---|---|---|
| `ratio_ma_type` | integer | Ratio | Moving-average type, as an **ordinal** into the TA-Lib `MAType` enum (§7). Out-of-range rejects the file. |
| `ratio_ma_period` | number | Ratio | Moving-average period. |
| `ratio_stddev_period` | number | Ratio | Standard-deviation period. |
| `ratio_entry_mode` | number | Ratio | `0` simple, `1` uptick, `2` downtick. |
| `ratio_rsi_period` | number | Ratio | **Optional**, defaults to `10`. RSI filter period. |
| `ratio_rsi_threshold` | number | Ratio | **Optional**, defaults to `0` (filter disabled). |
| `residual_linreg_period` | number | Residual | OLS regression window. |
| `ka_ve` | number | Kalman-auto | Observation covariance. |
| `ka_usage_target` | number | Kalman-auto | Usage target, percent. |

The two RSI fields are the only strategy fields that may be omitted entirely. If
present they must still be numeric (or `null`).

### 4.4 Extra entry/exit rules

Each rule is a flag plus its value. The flag is read as "enabled if equal to 1",
so `1`/`0` and `true`/`false` both work.

| Field | Type | Meaning |
|---|---|---|
| `enable_max_days` / `max_days` | flag / number | Close a position after this many days. |
| `enable_min_pl` / `min_pl` | flag / number | Minimum P/L required before closing. |
| `enable_min_price` / `min_price` | flag / number | Minimum price of either leg required to enter. |
| `enable_min_profit_potential` / `min_profit_potential` | flag / number | Minimum expected profit required to enter. |
| `allow_reversals` | flag | Allow a direct long↔short reversal. |

### 4.5 Trading windows

| Field | Type | Meaning |
|---|---|---|
| `entry_start_hour`, `entry_start_minute` | number | Start of the window in which entries are allowed. |
| `entry_end_hour`, `entry_end_minute` | number | End of that window. |
| `exit_start_hour`, `exit_start_minute` | number | Start of the exit window. |
| `exit_end_hour`, `exit_end_minute` | number | End of the exit window. |
| `timezone` | string | Time-zone ID the eight values above are expressed in, e.g. `America/New_York`. Must be a zone the Joda-Time database knows; an unknown one rejects the file. |

Hours are 24-hour clock. Note that the example file uses `15:30`–`15:55` in
`America/New_York` — these are wall-clock times in the stated zone, not UTC.

### 4.6 Sizing and maintenance

| Field | Type | Meaning |
|---|---|---|
| `ticker1margin` | number | Margin requirement for leg 1, percent. |
| `ticker2margin` | number | Margin requirement for leg 2, percent. |
| `slot_occupation` | number | How many portfolio slots this pair consumes (`1` = one slot). Values below `0.01` prevent the pair from ever acquiring a slot. |
| `allow_positions` | number | `0` both directions, `1` long only, `2` short only. |
| `status` | number | `0` inactive, `1` maintain, `2` active. |

---

## 5. Symbol format

Both legs use Google-style `EXCHANGE:TICKER` symbols, e.g. `NASDAQ:CAKE`,
`NYSE:OMC`, `NYSEMKT:FAX`.

* Exactly one `:` — anything else is rejected.
* The exchange must be one of **`NYSE`, `NASDAQ`, `NYSEARCA`, `NYSEAMEX`,
  `NYSEMKT`**. All map to USD. Any other exchange rejects the file; there is no
  support for non-US instruments.
* A `.` in the ticker becomes a space when the broker contract is built
  (`RDS.A` → `RDS A`), so write it with the dot.

---

## 6. Types, and what gets rejected

The importer validates the **whole file before importing any of it**. If anything
fails, nothing is imported — there is no partial import — and the error message
names the portfolio or the offending strategy.

A file is rejected when:

* it is not valid JSON, is empty, or is not an object/array of objects;
* a portfolio or strategy is missing any required field (§3, §4);
* a field that should be numeric holds a string or other non-numeric value;
* `model` is not one of the four recognised names;
* `ratio_ma_type` is not an integer in range (§7);
* `timezone` is not a known zone ID;
* either symbol is unparseable or names an unsupported exchange;
* `strategies` is missing or is not an array.

Two notes on types:

* **Booleans are accepted anywhere a number is expected.** PTL Trader's own export
  writes the `enable_*` flags as `true`/`false`, so both spellings round-trip.
* **Numeric values are not range-checked.** The validator's job is to refuse what
  would fail to load or be silently misread — a non-numeric value would otherwise
  become `0` without warning. A numeric but nonsensical value (`entry_start_hour`
  of `99`, a negative period) passes validation. Getting the values *right* is the
  author's responsibility.

---

## 7. `ratio_ma_type` values

This is an ordinal into TA-Lib's `MAType` enum, not a name. Writing `"Ema"` is
rejected; write `1`.

| Value | Type |
|---|---|
| `0` | SMA — simple |
| `1` | EMA — exponential |
| `2` | WMA — weighted |
| `3` | DEMA — double exponential |
| `4` | TEMA — triple exponential |
| `5` | TRIMA — triangular |
| `6` | KAMA — Kaufman adaptive |
| `7` | MAMA — MESA adaptive |
| `8` | T3 |

Values outside `0`–`8` reject the file.

## 9. A note on the CSV export

The PTL website also offers a **CSV** export (an example is in `example.csv`).
**PTL Trader cannot import CSV** — there is no CSV importer, only the JSON one
described here.

The CSV form is also lossy: it omits `uid`, `status`, `downtick_threshold`,
`allow_reversals`, `trade_as_1`/`trade_as_2` and every portfolio-level field. It
remains useful for spreadsheet analysis, but **export JSON, not CSV, if you intend
to migrate.** If all you have left is a CSV, the missing values must be supplied
by hand against the tables above before it can be turned into an importable file.
